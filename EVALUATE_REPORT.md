## Executive Summary

Alex is a well-architected multi-agent financial planning platform with solid foundational patterns: clean agent separation of concerns, Bedrock LLM integration via LiteLLM, Aurora Data API for serverless database access, Clerk JWT authentication, and dual deployment via Cloudflare Pages + CloudFront. The codebase is functional and demonstrates strong async orchestration.

The **most critical findings** are two security vulnerabilities: (1) a CORS configuration that falls through to wildcard `["*"]` when "localhost" appears in the env var, allowing any website to call the production API; and (2) a debug `/test-bedrock` endpoint on the Researcher App Runner service that leaks AWS configuration to unauthenticated callers.

The **biggest opportunity** is hardening the security posture to match financial-grade requirements — adding audit logging, UUID validation, input sanitization, and XSS protection. The platform also suffers from ~200+ lines of duplicated boilerplate across agents and 18-25% test coverage.

**Recommended first action**: Fix the CORS logic and remove the debug endpoint — 30 minutes of work, zero risk, eliminates the two Critical-severity findings.

## Domain Detail

### Architecture & Code Quality

**Finding 1: Observability module copy-pasted across 5+ agents**
- Evidence: `backend/planner/observability.py`, `backend/reporter/observability.py`, `backend/tagger/observability.py`, `backend/charter/observability.py`, `backend/retirement/observability.py`
- Each agent has a near-identical 113-line `observability.py`. The only differences are `service_name` (e.g., "alex_planner_agent" vs "alex_reporter_agent") and the flush sleep time: planner sleeps 15 seconds, reporter sleeps 10 seconds. This inconsistency means trace flush reliability varies by agent.
- Recommendation: Extract to a shared `backend/common/observability.py` with parameterized service name. Use a configurable flush timeout.

**Finding 2: Lambda handler boilerplate duplicated across 4 agents**
- Evidence: `backend/planner/lambda_handler.py`, `backend/reporter/lambda_handler.py`, `backend/charter/lambda_handler.py`, `backend/retirement/lambda_handler.py`
- ~100 lines of identical structure: `with observe()`, event parsing, `json.loads` fallback, `job_id` extraction, `Database()` init, `asyncio.run()`, error return formatting. Only the agent-specific call differs.
- Recommendation: Create a `@lambda_agent_handler` decorator or factory that handles the boilerplate.

**Finding 3: Model configuration duplicated across 6 files**
- Evidence: `backend/planner/agent.py:267-272`, `backend/reporter/agent.py:577-584`, `backend/tagger/agent.py:176-181`, `backend/charter/agent.py:169-178`, `backend/retirement/agent.py:275-281`, `backend/reporter/judge.py:21-28`
- Same 5-line pattern: `model_id = os.getenv(...)`, `bedrock_region = os.getenv(...)`, `os.environ["AWS_REGION_NAME"] = bedrock_region`, `model = LitellmModel(...)`.
- Recommendation: Extract to `backend/common/model.py` with `create_bedrock_model()` factory.

**Finding 4: No request correlation IDs across service boundaries**
- Evidence: `backend/planner/agent.py` (Lambda invocations), `backend/reporter/lambda_handler.py` (logging)
- `job_id` exists in all agents but is not included in structured log entries. When the Planner invokes Reporter, Charter, and Retirement in parallel, there's no way to correlate log entries across CloudWatch log groups.
- Recommendation: Pass `job_id` as a logging context field; use `logging.extra` or structured JSON logging.

**Finding 5: reporter/agent.py is 664 lines**
- Evidence: `backend/reporter/agent.py`
- Mixes: formatting functions (format_fundamentals, format_economic_context, format_technical_indicators), S3 Vectors query logic, SageMaker sentiment calls, agent creation, tool definitions.
- Recommendation: Extract to `reporter/formatters.py` and `reporter/data_sources.py`.

**Finding 6: api/main.py is 644 lines**
- Evidence: `backend/api/main.py`
- Mixes: CRUD routes for users/accounts/positions/instruments/jobs, SQS job queueing, test data population, auth middleware. Should be split into route modules.

### Feature Gaps & Enhancement Opportunities

**Finding 13: No job cancellation mechanism**
- Evidence: `backend/api/main.py` (job status values: pending, running, completed, failed)
- Users cannot cancel a running analysis. A 2-minute analysis blocks the user with no escape.
- Recommendation: Add `cancelled` status + cancellation endpoint + polling check in agent loops.

**Finding 14: No caching for market data**
- Evidence: `backend/planner/market.py`, `backend/market_data/src/market_data/fmp.py`, `backend/market_data/src/market_data/fred.py`
- FMP fundamentals, FRED economic indicators, and Polygon prices are fetched fresh every analysis run. FRED data changes monthly; FMP data changes quarterly. Adds ~10-15 seconds of API latency per analysis.
- Recommendation: Cache with TTL — FRED 24h, FMP 6h, Polygon 5min.

**Finding 15: AnalysisProgressTracker component built but unused**
- Evidence: `frontend/components/AnalysisProgressTracker.tsx`
- Comprehensive progress tracking UI with polling, elapsed time display, and agent status. Not integrated into `advisor-team.tsx` or `analysis.tsx`. Users see minimal progress during 2+ minute analyses.

**Finding 16: Monte Carlo retirement simulations not reproducible**
- Evidence: `backend/retirement/agent.py`
- No `random.seed()` set. Same portfolio analyzed twice produces different retirement projections. Makes debugging and comparison impossible.

**Finding 17: No error tracking service**
- Evidence: `frontend/pages/_app.tsx`
- No Sentry, LogRocket, or similar service. Frontend errors are invisible to the development team. Users encounter errors silently.

**Finding 18: No retry logic on frontend API calls**
- Evidence: `frontend/lib/api.ts`
- Failed API calls display an error message with no automatic retry. Transient network errors require manual page reload.

**Finding 19: Database schema has no version tracking**
- Evidence: `backend/database/run_migrations.py`, `backend/database/migrations/001-005`
- Migrations are numbered files run sequentially. No `schema_version` table to track which migrations have been applied. Rerunning migrations relies on `IF NOT EXISTS` guards.

**Finding 20: No CI coverage thresholds enforced**
- Evidence: `.github/workflows/test.yml`
- Tests run in CI but no `--cov-fail-under` flag. Coverage could drop to 0% without blocking PRs.

### Security & Compliance

**Finding 21: CORS wildcard allows any website to call API**
- Evidence: `backend/api/main.py:58-59`
- ```python
  if cors_origins_env == "*" or "localhost" in cors_origins_env:
      cors_origins = ["*"]
  ```
- If `CORS_ORIGINS` is set to `"http://localhost:3000,https://finance.kentbenson.net"`, the check `"localhost" in cors_origins_env` is True, and CORS falls through to `["*"]`. Any website can make authenticated API calls from a user's browser.
- **Fix**: Remove the `"localhost" in` check. Use exact origin matching always.

**Finding 22: Debug /test-bedrock endpoint leaks AWS configuration**
- Evidence: `backend/researcher/server.py:212-216`
- ```python
  "env_vars": {
      "AWS_REGION_NAME": os.environ.get("AWS_REGION_NAME"),
      "AWS_REGION": os.environ.get("AWS_REGION"),
  }
  ```
- The `/test-bedrock` endpoint is accessible without authentication on the App Runner service. Returns AWS region, model ID, and configuration details.
- **Fix**: Remove the endpoint or gate it behind authentication.

**Finding 23: UUID validation missing for all ID parameters**
- Evidence: `backend/api/main.py` (account_id, job_id path parameters), `backend/planner/agent.py` (job_id from SQS)
- Per CLAUDE.md security baseline: "Validate all IDs with UUID regex: `^[0-9a-f]{8}-...`". Not implemented anywhere.
- **Fix**: Add a `validate_uuid()` dependency to all route handlers with ID parameters.

**Finding 24: No audit logging for financial data mutations**
- Evidence: `backend/api/main.py` (all CRUD endpoints)
- Account creation, position changes, portfolio deletions, and analysis requests are not logged in an audit trail. For a financial planning platform, this is a compliance gap.
- **Fix**: Add structured audit log entries for all user-initiated mutations.

**Finding 25: Markdown rendered without XSS sanitization**
- Evidence: `frontend/pages/analysis.tsx:284-311`
- `react-markdown` is used to render agent analysis output. No `allowedElements` whitelist is configured. If a compromised agent returns malicious markdown with embedded HTML, it could execute in the user's browser.
- **Fix**: Configure `react-markdown` with explicit `allowedElements` whitelist.

**Finding 26: Symbol input not validated against ticker format**
- Evidence: `backend/api/main.py:401-427`, `frontend/pages/accounts/[id].tsx:253`
- Symbol creation uses `.upper()` but no format validation. Could accept 100-character strings or special characters.
- **Fix**: Validate with regex: `/^[A-Z0-9.\-]{1,10}$/`

**Finding 27: Researcher /research endpoint has no authentication**
- Evidence: `backend/researcher/server.py`
- The App Runner service accepts research requests from anyone who knows the URL. Only `x-api-key` header used (non-standard, easy to leak).
- **Fix**: Use `Authorization: Bearer <token>` with API key validation.

**Finding 28: IAM wildcard regions for Bedrock**
- Evidence: `terraform/6_agents/main.tf` — `"arn:aws:bedrock:*::foundation-model/*"`, `"arn:aws:bedrock:*:*:inference-profile/*"`
- Grants Bedrock access across all AWS regions. Should be scoped to the specific regions used.

### Performance & Scalability

**Finding 29: Observability sleep(10-15s) wastes Lambda billed time**
- Evidence: `backend/planner/observability.py:106-107` (15s), `backend/reporter/observability.py:105-106` (10s)
- After each agent execution, the Lambda sleeps 10-15 seconds to allow Langfuse trace flush. At $0.0000166667/GB-second for 2GB Lambda, this adds ~$0.003-$0.005 per invocation. With 5 agents per analysis, that's ~$0.015-$0.025 wasted per analysis.
- **Fix**: Use Lambda Extensions for async flush, or reduce to 2-3 seconds with `flush()` callback.

**Finding 30: Dashboard makes 8+ API calls on page load**
- Evidence: `frontend/pages/dashboard.tsx` (useEffect data loading)
- Loads: GET /api/user, GET /api/accounts, then for each account: GET /api/accounts/{id}/positions, plus GET /api/jobs. For 5 accounts = 8 API calls with no batching or parallel optimization.
- **Fix**: Add batch endpoint or use React Query for automatic deduplication.

**Finding 31: calculatePortfolioSummary not memoized**
- Evidence: `frontend/pages/dashboard.tsx:338`
- Iterates through all positions and instruments on every render. Should be wrapped in `useMemo`.

**Finding 32: Memory leaks in frontend interval cleanup**
- Evidence: `frontend/pages/advisor-team.tsx:150-155`
- Polling interval created for job status checking. If `currentJobId` changes, a new interval is created but the old one may not be properly cleaned up, causing accumulating intervals.
- **Fix**: Clear existing interval before creating new one; ensure cleanup in useEffect return.

**Finding 33: Lambda package at 250MB limit**
- Evidence: `backend/planner/package_docker.py` (EXCLUDE_PREFIXES list of 30+ packages)
- All 5 agents package to ~82MB zipped by aggressively excluding numpy, pandas, scipy, and unused AI provider SDKs. Adding one more heavy dependency (e.g., for improved charting) would exceed the limit.
- **Fix**: Plan migration to Lambda container images (10GB limit) before next major feature.

**Finding 34: Sentiment batch analysis is sequential**
- Evidence: `backend/market_data/src/market_data/sentiment.py:107-117`
- `analyze_batch()` calls `self.analyze(text)` in a sequential loop. For 10 texts, this serializes 10 SageMaker invocations.
- **Fix**: Use `asyncio.gather()` or `concurrent.futures.ThreadPoolExecutor` for parallel invocation.
